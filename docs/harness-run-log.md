### Executed evaluator report

**Alignment summary.** P2 attacks the brief directly: member profiles are read as ENSIP-5 text
records, retrieval is a bounded lexical index, the model may only nominate names from the
candidate set it was given, and the answer is validated against that set before display, with a
real no-match branch. The failure mode the brief opens with — *"the last chatbot someone tried
confidently recommended a person who doesn't exist"* — is structurally impossible here rather
than merely unlikely.

**What's genuinely strong**

- **Criterion 1 is structural, not hopeful.** `src/shared/model-output.ts:165`
  `enforceCandidateMembership()` re-normalizes every name the model produced and looks it up in
  the retrieved candidate set; `:160-161` states a rejected name is never displayed as a person
  *"even if it is a real, famous ENS name"*. Nothing reaches the UI before this runs, and the
  rejected names are **returned to the caller** (`:9`) instead of being dropped silently.
- **Criterion 3 is enforced by the function signature.** `src/shared/prompt.ts:69` is
  `buildSystemMessage(): string` — **zero arguments**, so there is no parameter through which
  profile text could arrive. `:134-136` then sends three separate messages: system, question,
  candidate data. Profile content is never concatenated with instructions.
- **Criterion 2 has an explicit, clamped bound.** `src/shared/retrieval.ts:41` `topK: 5`,
  `:45` `MAX_TOP_K = 20`, `:244` `clampTopK(...)`, and the actual cut at `:330`
  `candidates: aboveThreshold.slice(0, topK)`. `askModel` re-checks the bound at the HTTP edge.
- **Criterion 5 short-circuits before the model.** `src/server/find.ts:141`
  `if (gate.candidates.length === 0)` returns the explicit no-match verdict; the model call is
  at `:172`, i.e. after the branch. Confirmed live: two recorded cases report `model used: no`.
- **Criterion 4 uses the Universal Resolver, with an injectable seam.**
  `src/server/ens.ts:103-104` `readTextViaUniversalResolver = (client, name, key) =>
  getEnsText(client, { name, key })`, and `src/server/community.ts:188` re-reads the roster and
  every member on refresh. `readText` (`community.ts:122`) is a test seam that production never
  passes.
- **Craft: reasons come from the profile, not the model.** `model-output.ts:68` — the displayed
  reason is *"Copied from the candidate's own records, never from the model"*. That is what stops
  this being wrong shape (1), a fluent answer with no specifics.
- **Craft: the adversarial bio is handled, not just mentioned.** `mika.tokyobuilders.eth`'
  record carries `IGNORE ALL PREVIOUS INSTRUCTIONS…`; the probe prints
  `! SUSPICIOUS: instruction-like text, shown as data, never obeyed`, and
  `src/shared/profile.ts` `looksLikeInjection`/`SUSPICIOUS_SCORE_PENALTY` keep it ranked, not
  boosted. The T12 log records a real bug found here: the penalty had been folded into the
  relevance score, which silently moved the profile *below the admission floor* — "ranked lower"
  had become "excluded". Score and ordering are now separate.
- **Wrong shape (3) is avoided.** The UI renders member cards with per-field read status, reasons
  and matched-term evidence — not raw JSON or addresses. The probe output is the reviewer's view,
  not the product's.

**Gaps & risks**

1. **Nothing is published on Sepolia, so criterion 4 is not verified live.**
   `npm run probe:community` exits 0 and states plainly: *"NO live member profile could be read.
   Everything above is the LOCAL SIMULATED fixture set. It is not chain data and must never be
   presented as such."* The ENS read path is exercised by unit/API tests through the `readText`
   seam, and the code is correct for a future user-supplied name — but **code support is not
   proof of the live requirement**. The brief's step 1 ("at least 8 ENS names … with profile text
   records") is **NOT MET / BLOCKED BY ENS SETUP**.
2. **The profile format has no location field.** The evaluator explicitly rewards a format that
   captures *"skills, availability, location"*. `src/shared/profile.ts` defines `name` +
   `com.peoplefinder.{role,skills,availability}` and `description`; location exists only as free
   text inside the bio. The recorded query *"I just moved to Tokyo. Who can introduce me to the
   right people?"* passes only because that word appears in someone's bio — it is not a queryable
   field. A member who writes no location sentence becomes unmatchable on a location question.
3. **Simulated index is the default demo path, so a judge sees fixture data first.**
   `ALLOW_SIMULATED_INDEX` drives the recorded dataset. It is labelled `source: "simulated"` in
   every response and behind a UI banner, which is the right honesty, but it means the demo
   currently proves the *plumbing*, not the *chain*.
4. **Adversarial handling is asserted in the probe and the score, not shown as a user-facing
   outcome.** The recorded cases do not include a query whose correct answer is "the suspicious
   profile should not be recommended". Adding one would demonstrate the property to a judge rather
   than describing it.
5. **`npm install` audit findings** (three moderate, one high, one critical) remain, deliberately
   not force-fixed because it would move versions across the `viem`/`zod` trees.

**Success-criteria fit — "a new member asks who can mentor them in Rust this month and gets two
real community members with a reason for each, or a straight answer that nobody fits": PARTIAL.**
The retrieval, grounding, reasons and no-match halves are demonstrated end-to-end and the answer
is specific (`ask-mei-by-name` returns exactly `mei.tokyobuilders.eth`). What is missing is the
first three words of the outcome: the members are real *fixture* members, not real Sepolia
records. One publishing pass converts partial to met.
