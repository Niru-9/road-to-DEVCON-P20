## What is recorded

Each case names the community members it must return, or states `expect: "no-match"`.
`mustNotInclude` is enforced as hard as `mustInclude`; `mayInclude` is deliberately not an
assertion, because a reasonable answer may contain more than the minimum.

Each case is checked in **two independent halves**, because they fail for different reasons:

1. **Reachable (no model).** Computed from the index alone: is the expected member inside the
   top-k bound, after the availability gate? Retrieval and the gate are pure functions, so
   this half is reproducible. A `NO` here means the expectation is unreachable — a defect in
   the case or in retrieval, never a statement about a model.
2. **Observed (model).** What the configured model actually returned, and whether it matched
   the expectation. This half depends on the model named below and can change with it.

- Problem: `community-people-finder`
- Community root: `tokyobuilders.eth`
- Candidate bound in force: top-k **5**, relevance floor **1**
- Roster record: `com.peoplefinder.members`
- Profile records: `name`, `com.peoplefinder.role`, `com.peoplefinder.skills`, `com.peoplefinder.availability`, `description`
- Retrieval is deterministic lexical scoring; defaults {"topK":5,"minScore":1}

> **The run below used the SIMULATED index.** No member record was readable on Sepolia,
> so the app answered from the labelled local fixture set. The results demonstrate the
> application logic; they are not evidence about published ENS records.
